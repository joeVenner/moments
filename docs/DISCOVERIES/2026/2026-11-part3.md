# Discoveries — November 2026 (part 3)

## [2026-11-18] Context Update — iOS picked media import (MediaPipeline)
- **What changed:**
  - `PickedMedia` is the PhotosPicker `Transferable`. It has two `FileRepresentation`s, movie first and then image, so a Live Photo yields its still.
  - Each representation copies the picker's short-lived file into `Caches/PickedMedia/<UUID>.<ext>`. The folder is protected (`completeUntilFirstUserAuthentication`) and excluded from backup. Links, folders and files over 4 GB are refused, free space is checked first, and a failed copy is removed.
  - `MediaImporter.importMedia(_:into:)` prepares the copy into the item's staging folder as `photo.jpg` or `video.mp4`. It sweeps `.preparing` leftovers first and replaces any earlier attempt's file.
  - Problems are `unsupported`, `tooLarge`, `failed`, `cancelled`, `noSpace` and `busy`. Only one import may run per folder at a time.
- **Why:**
  - The picked copy still carries GPS. It is deleted on success and on failures that can never work (`unsupported`, `tooLarge`).
  - After `failed`, `cancelled` or `noSpace` it is kept, so the same pick can be retried without reloading a large video. The caller calls `discard(_:)` when giving up.
  - `PickedMedia.clearInbox()` must run at launch, before the picker can be shown, because it would delete the files of imports in progress.
  - The picker may hand over the user's own file, so it is always copied, never moved. APFS clones the copy, so it doesn't double disk use.
- **Impact:** `ios/MomentsKit/Sources/MediaPipeline/MediaImporter.swift` and `MediaImporterTests`. To glue it to the queue: `QueuedUpload.StagedFile(relativePath: StagingArea.relativePath(for: id, name: media.name), size: media.byteCount, contentType: media.contentType)`. That glue lives where both modules are imported.
- **Reference:** branch `feat/ios-media-import`.

## [2026-11-18] Context Update — iOS guest upload screen (FeatureGuest)
- **What changed:**
  - **`UploadModel`:** prepares picks one at a time, each in its own task so removing it cancels it. A picker failure keeps the loader, so a retry reloads the pick. Ready items are shared with an optional caption through `UploadSubmitting.submit -> SubmitResult` (`accepted`, `duplicate`, `full`, `invalid`, `failed`). The caption is checked as the server checks it: 500 UTF-16 units, no control characters except line breaks. A batch holds at most 30 picks.
  - **`UploadView`:** the system PhotosPicker with `.current` encoding, so we get originals. Each pick has a tile showing its state, the problem and a Try again. A note says videos keep their sound. There is a caption field and a Share button.
  - **`GuestEventView`:** shows a share button in the Moments and Highlights tabs only when `GuestDependencies.uploads` is set. It is nil in the app until uploads are wired.
  - **`AppEnvironment.live()`:** calls `GuestUploadsLaunch.clearLeftovers()`, which clears the picked-originals inbox.
- **Why / lessons:**
  - Sharing must be atomic from the UI's side. Remove, Cancel or swipe-dismiss during `share()` used to crash, because the loop indexed `items`. It also deleted folders the queue had just taken. Mutations are now refused while sharing, and closing waits for the share to end.
  - `current` can outlive its job for a moment. Only a pick still `.preparing` may be left to its job to clean up.
  - `EnqueueError.duplicate` means the item was already queued, so treat it as success.
- **Before wiring `UploadDependencies`:**
  - Add a launch sweep that deletes every staging `<UUID>` folder not in the loaded queue, to cover prepared files of items never shared before a kill.
  - Add an adapter that maps `UploadQueue.EnqueueError` to `SubmitResult`.
  - Cleanup now runs on the sheet's `onDismiss`, not `onDisappear`; check on a device that it fires on swipe-dismiss.
- **Follow-ups:**
  - Server-side: strip or refuse bidi and zero-width characters in captions (U+202A–202E, U+2066–2069, U+200B–200F), then mirror that in `cleanCaption`.
  - Add a loader timeout for stalled iCloud downloads.
- **Reference:** branch `feat/ios-upload-screen`.

## [2026-11-18] Context Update — guest join rate limit
- **What changed:**
  - New `JOIN_LIMITER` rate-limit binding (namespace `1005`, 60 per 60 s), keyed `<eventId>:ip:<CF-Connecting-IP>`. It is declared in `wrangler.jsonc` and needs no Cloudflare resource created.
  - `joinEventAsGuest` takes an `isLimited` callback. It is asked only after the "re-join with the current token" early return and before the claim batch, so returning guests cost no budget and a refused join writes nothing.
  - The web and v1 join routes both answer `429 rate_limited` with `Retry-After: 60`; the OpenAPI spec documents it.
  - iOS: `MomentsClient.join` maps 429 to `.rateLimited`. `JoinModel` shows `NicknameProblem.busy` for a new join; a returning guest's automatic re-join keeps the stored identity and ends at `.failed(.temporary)`.
- **Why / lessons:**
  - The app re-joins on every open, so limiting every join would block venue Wi-Fi crowds that mint nothing. Limit only the minting path.
  - A rate limit bounds speed, not total: 40 guests × 50 open uploads still fill the 2000 per-event open-upload cap inside one window.
- **Required before the app ships (security audit, MEDIUM):** cap guests per event (for example refuse a new claim past N sessions) or add a per-event aggregate limiter; make the open-upload cap fair (few open uploads until a guest completes one, or reserved capacity); give stale open sessions a short TTL. A per-source cap that stores an IP-derived value (HMAC) needs Yassir's OK first.
- **Follow-ups:**
  - Web `joinEvent` treats any non-OK answer as success, so a limited web guest silently gets no token. Fix before the `GUEST_TOKENS_ENFORCED` flip.
  - Key IPv6 clients by their /64 prefix.
  - The legacy web upload path still creates participants without any limit.
- **Reference:** branch `feat/v1-join-limit`.

## [2026-11-18] Context Update — caption text-direction characters
- **What changed:** `src/worker/captionText.ts` holds the caption rule. The v1 upload-session caption refuses controls (except LF and CR) and the bidi embeddings, overrides and isolates U+202A–202E and U+2066–2069. The three web upload routes drop those bidi characters with `cleanWebCaption` instead of refusing them. iOS `UploadModel.cleanCaption` mirrors the v1 rule.
- **Why / lessons:** the follow-up asked to refuse U+200B–200F too, but those are needed text: U+200D joins emoji (👩‍👧), U+200C is required in Persian, and U+200E/200F mark direction in Arabic and Hebrew. Only the reordering controls enable spoofing such as `gift<RLO>txt.exe`, so only they are blocked. Web captions are read by every client, so they are cleaned too, without refusing anything.
- **Follow-ups (low):** U+061C, C1 controls, U+2028/2029, U+2060–2064, U+FEFF and astral tag characters (U+E0000–E007F, needs the `u` flag) are not covered. Captions already stored are not cleaned.
- **Reference:** branch `feat/caption-invisible-chars`.

## [2026-11-18] Context Update — guest leave and delete
- **What changed:**
  - `src/worker/guestLeave.ts` `leaveEvent` and `DELETE /api/v1/events/{slug}/participants/me`. Each call aborts up to 10 of the guest's open sessions and deletes their objects, then deletes up to 90 owned moments (one R2 batch delete, then reactions and rows; the tombstone trigger tells the feed). It returns `{done}`. A final D1 batch deletes the guest's `uploads` rows, `guest_sessions` and participant, each guarded by `NOT EXISTS` open sessions or owned moments.
  - `eventGate` lets exactly `DELETE …/participants/me` through without an access grant; the handler still needs the guest token.
  - `startUpload`'s insert requires the participant to still exist. Otherwise it returns `guest_gone`, which the route maps to 403 `guest_required`.
  - iOS: `LeaveService`/`MomentsClient.leaveEvent`; `LeaveModel` loops up to 60 steps and forgets the stored credentials only when done. `guestRequired` and `eventNotFound` count as done. `GuestEventView` has an event menu, a confirmation, a full-screen progress scrim and a failure alert; `RootView` returns to the placeholder.
- **Why / lessons:**
  - Owned means "made from a session this guest's token opened" (`uploads.participant_id` joined on `media_url = '/media/' || key`). Deleting by nickname would let whoever claims a legacy name erase the real owner's web photos. Web uploads never carry a token, so they stay.
  - Abort open sessions first: the finalize sweep needs no token and would otherwise create moments after the guest left. Revoke last, so a retry after a lost answer still authenticates.
  - D1 allows at most 100 bound parameters per statement: keep `IN` batches under it.
  - Run the full `npm test` after touching shared SQL; targeted runs missed 39 failures in other suites (their tests had no participant rows).
- **Accepted:**
  - Reactions the guest made stay; reactor ids are client-chosen.
  - Before enforcement, a guest who claimed a legacy name deletes that participant row on leave (the claim had taken it over).
  - Web moments left under a freed name count for whoever claims it next.
- **Before wiring uploads:** cancel the event's queued and in-flight uploads (UploadQueue) when Leave starts. Server-side, `startUpload` refuses afterwards, but a running upload could still complete.
- **Follow-ups:** pause the feed, highlights and leaderboard polling while leaving; a test for a failure to remove the credentials; check the top menu row on a device (space, stacking with the unsaved banner).
- **Reference:** branch `feat/guest-leave`.

## [2026-11-18] Context Update — web join refusals
- **What changed:** `joinEvent` (web) returns a `JoinOutcome` (`lib/joinOutcome.ts`). `NicknameGate` awaits it, keeps the form open on `rate_limited` / `nickname_taken` with a `role=alert` message (EN+FR), and caps the input at 60 characters. `EventPage` saves the nickname only after the join.

## [2026-11-18] Context Update — iOS French
- **What changed:**
  - `ios/Moments/Localizable.xcstrings` (EN source + FR) holds the strings of the app **and** the FeatureGuest package. Package keys are marked `extractionState: manual`.
  - `MomentsTests/LocalizationTests` (app-hosted, simulator) checks:
    - every key has translated French with the same `%lld`/`%@` placeholders;
    - French resolves through Bundle.main, including the plural forms ("1 demande / 3 demandent votre attention");
    - inflection via AttributedString ("3 nouveaux souvenirs").
  - `npm run ios:strings:check` (`scripts/check-ios-strings.mjs`, manual, macOS) runs `xcodebuild -exportLocalizations` and fails on any key missing from the catalog.
- **Why one app catalog, not `bundle: .module`:**
  - SwiftUI string-key APIs in a package (`Text`, `Button`, `Label`, `ProgressView`, `navigationTitle`, ternaries…) resolve against Bundle.main.
  - A per-module catalog would need about 150 call sites rewritten to `LocalizedStringResource(…, bundle: #bundle)`, and every missed site silently stays English.
  - The app catalog has no such hole.
  - The cost: package-only hosts (tests, previews) show English.
- **Lessons:**
  - SwiftPM on the command line copies `.xcstrings` uncompiled. Only Xcode builds compile it (`fr.lproj`), so FR runtime tests must run under `xcodebuild`, in the app-hosted target.
  - `String(localized:)` does **not** apply Markdown: `^[…](inflect: true)` comes back raw. Use `AttributedString(localized:)` (what `Text` does). This caused a real bug: FeedView's VoiceOver announcement.
  - `LocalizedStringResource.locale = fr` plus `String(localized:)` is a reliable way to test a language without changing the simulator.
  - On iOS 17, `TextField(LocalizedStringResource, text:)` needs iOS 26. Use `TextField(text:prompt:label:)`.
  - French: a no-break space (U+00A0) before `? ! :` and `%`.
- **Rules:**
  - Any new target that links FeatureGuest (the **App Clip**) must include `Localizable.xcstrings`.
  - Run `npm run ios:strings:check` after adding UI text, and translate whatever it reports.
- **Follow-ups:** InfoPlist strings (none needing translation yet; PhotosPicker needs no permission text); "pseudo" (iOS and the web join message) vs "nom" in older web copy.
- **Reference:** branch `feat/ios-localization`.

## [2026-11-18] Context Update — web background rejoin
- **What changed:**
  - `lib/guestRejoin.ts` `rejoinIfTokenless`: after the event loads (so a private event is already unlocked), a saved nickname with no guest token joins again.
  - It runs once per tab, guarded by a sessionStorage flag set before the request so a double mount sends one join. The avatar seed is sent empty.
  - `nickname_taken` (only with enforcement on) drops the saved nickname and reopens `NicknameGate` with `initialProblem`.
  - `unavailable` clears the flag, so the next load retries; `rate_limited` does not.
- **Why:** before the `GUEST_TOKENS_ENFORCED` flip, legacy web guests and guests whose join failed must claim their name while it is still unclaimed.
- **Lessons:** clear the stored nickname even when the effect is stale, because the tab's "tried" flag is already spent. Otherwise a StrictMode double mount could leave a stolen nickname in use.
- **Accepted:**
  - A guest who lost the name before enforcement (joined, no token) re-POSTs once per new tab. That costs one JOIN_LIMITER slot, out of 60 per minute per event and IP.
  - A guest whose first join never reached the server is created with no avatar seed; the strip shows initials.
- **Still before the flip:** web uploads and reactions don't send or require the token (only join claims are enforced). Requiring them is part of the flip work, together with binding the reactor id server-side.
- **Reference:** branch `feat/web-guest-rejoin`.

## [2026-11-18] Context Update — hearts bound to the guest session
- **What changed:**
  - Migration 0017 adds `guest_sessions.reactor_id`, plus a partial unique index on `(event_id, reactor_id)`.
  - `reactions.ts` `gateReaction` is shared by the web toggle and the v1 add/remove routes. It checks `guest_required` (only when enforced), then `REACTION_LIMITER` (keyed on the session, else the IP), then `bindReactor`. It returns the reactor id to write under.
  - The web toggle validates `REACTOR_ID_PATTERN` and writes through `setReaction`, so a double tap can no longer 500. The web client sends `X-Guest-Token` on the toggle, and `MomentCard` swallows refusals.
- **How binding works:**
  - The first heart binds the session.
  - A different id later (iOS keeps the token in the keychain but the reactor secret in UserDefaults, so a reinstall splits them) **moves** the session's hearts in the event to the new id. They move, not copy, so counts can't inflate.
  - Every move statement re-checks that the session is still bound as read and the new id is free. A lost parallel race therefore moves nothing and writes under the winner's id, leaving no orphans.
  - An id held by another session is never bound or moved. The write uses it as a tokenless one would, which covers one browser joining twice.
- **Accepted until the flip:** omitting the token skips binding entirely. Reads (`reacted`) still use the client id. A token holder who learned another device's id (random, and never returned by the API, but present in web GET query strings and so in edge logs) before that device bound it could bind it first.
- **Re-audit leftovers (MEDIUM, closed only by the flip fix):**
  - Bind and write are still two transactions. Two parallel moves (X→Z2, then Z2→Z3) can leave R2's heart orphaned under Z2. This needs a flood of distinct ids; it is bounded by 60 a minute per session.
  - An unbound session presenting an id another session holds writes under it, just as a tokenless request can today.
- **For the flip:** derive the reactor from the session server-side and ignore the body id. Make leave delete the session's bound hearts (small follow-up PR).
- **Deploy order:** apply 0017 remotely **before** deploying. Without the column, every tokened heart 500s.
- **Reference:** branch `feat/bind-reactor-to-guest`.

## [2026-11-18] Context Update — web uploads send the guest token
- **What changed:**
  - `nickname.ts` `guestTokenHeaders(slug)` is spread into every same-origin web upload call:
    - `uploadMoment`;
    - multipart init, part-url, status, complete and abort;
    - Stream session, complete and abort;
    - the heart toggle.
  - The upload routes ignore the header today. Only the reaction gate and join read it.
- **Deliberately tokenless:**
  - R2 part PUTs: R2 CORS allows only Content-Type and Content-MD5, which also guards this.
  - tus: tus-js-client sends `headers` to the Stream upload URL as well, and the `?session=` id already ties tus to the guest.
- **Before enforcement covers web uploads:** the upload service worker resumes multipart uploads without localStorage, so those requests go tokenless. Persist the token in the `PersistedUpload` IndexedDB row (or pass it in from the page), and decide what a rotated or expired token means for a queued upload. Otherwise Background Sync retries forever.
- **Reference:** branch `feat/web-upload-guest-token`.

## [2026-11-18] Context Update — EventPage keyed on slug
- **What changed:** the default export of `EventPage.tsx` renders `EventPageForSlug key={slug}`.
- **Why:** React Router reuses the element across `/e/a` → `/e/b`. State the effect never reset (`event`, `notFound`, `accessRequired`, `tab`, `uploading`) and an in-flight join or rejoin could leak into the next event.
- **Notes:**
  - The resets inside the effect stay, because `accessVersion` re-runs on the same slug still need them.
  - Uploads started in A are not aborted on unmount. Their setters become no-ops, and the queue resumes them when the guest returns to A.
- **Reference:** branch `fix/event-page-keyed-by-slug`.
