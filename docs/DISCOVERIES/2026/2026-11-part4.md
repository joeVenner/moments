## [2026-11-19] Context Update — "join again" on a refused guest (slice d2b)
- **What changed:**
  - **Server, one rule:** a presented `X-Guest-Token` the server doesn't know (revoked by a leave, another event's, malformed) gets `403 {code: "guest_required"}`, enforced or not. This covers web upload init (`resolveWebUploader`), every upload follow-up and hearts (`gateReaction`, shared with v1). Only a *missing* token keeps the legacy path until `GUEST_TOKENS_ENFORCED`.
  - `webUploader.ts`: `mayUseUpload`/`mayFinishUpload` (booleans) became `uploadAccess`/`finishAccess` returning `"ok" | "not_found" | "guest_required"`, and `uploadRefusal` maps them to the response. Another guest's valid token on an owned row still reads as 404 "upload not found", so rows don't leak. Enforced plus tokenless on an owned row is now 403 instead of 404.
  - **Client:** `lib/guestRequired.ts`. The upload helpers (`multipartUpload` `jsonReq`, `streamUpload` `jsonRequest`) and `toggleMomentReaction` throw `GuestRequiredError(slug, sentToken)` and dispatch a `moments:guest-required` window event. `EventPage` listens and, **only if the refused token is still the stored one** (`refusalIsCurrent`), runs `forgetGuest(slug)` and shows the gate with `JoinProblem` `"guest_required"` ("join again", EN and FR).
  - Refused uploads are marked `failed`, aren't retried part by part, and aren't handed to Background Sync. The upload worker doesn't reject the sync for them.
- **Review and audit fixes:**
  - Security audit: **PASS**. Code review: WARN, no blockers. Fixes applied:
    - `refusalAction` replaces a plain token compare and returns:
      - `forget` when the refused token is the stored one;
      - `gate` when it was already cleared (left from another tab), so the gate shows without wiping anything;
      - `ignore` when another tab has joined again with a newer token, which is kept, and the refusal counts as an ordinary failure.
    - The upload worker relays refusals to open pages (`postMessage`, validated by `guestRequiredDetail`), because a worker has no `window`.
    - `refused` flag in the multipart worker pool, so a sibling part finishing late can't write a failed row back to uploading or paused.
    - The page's 15 s staged-resume retry skips refusals.
    - During and after a deliberate Leave, refusals are ignored (`isLeavingRef`, set via `LeaveEventButton.onLeavingChange`) until the browser joins again. A dedupe ref guards against several parallel parts reporting at once.
    - v1 reaction 403 description updated, `npm run openapi:update` run (description only).
  - **Accepted:**
    - an enforced tokenless call can tell "owned row exists" (403) from "no row" (404). That needs a 128-bit upload id plus its key, and doesn't reveal the owner.
    - `forgetGuest` drops every saved upload for the slug, as Leave does.
    - The tus create endpoint never checks the token; a dead Stream session there pauses and retries. Pre-existing; follow-up.
    - Stream-path unit tests are still missing: there is no tus harness.
- **Verified:** on local dev, join, then delete the event's `guest_sessions`, then tap a heart. The gate shows "You're no longer joined…", and the event's nickname and token are gone from localStorage.
- **Why:** with enforcement (or after a leave from another tab) a guest's writes would fail with a generic "upload failed" forever. The dead-token "404" is now an explicit 403, so a real 404 keeps meaning "this upload is gone".
- **Impact:** `src/worker/{webUploader,reactions,index}.ts`, `src/client/lib/{guestRequired,api,multipartUpload,streamUpload}.ts`, `uploadServiceWorker.ts`, `EventPage.tsx`, `NicknameGate.tsx`, `i18n.tsx`.
- **Reference:** branch `feat/web-guest-required`.

## [2026-11-19] Context Update — iOS leave drops queued uploads; refused hearts ask to join again (slice e2)
- **What changed:**
  - **Leave closes the event's uploads:**
    - `UploadQueue.beginLeaving(eventSlug:waitingAtMost:)` closes the event: `step` skips its items and `enqueue` throws `.leaving`.
    - It waits up to 10 s (or until cancelled) for a request already running, then removes every item of the event. That includes items still in flight, whose late answers are ignored, and records not loaded at launch (`QueueStore.removeRecords(eventSlug:excluding:)`). Staged files go too.
    - `endLeaving` reopens the event. Leaves are counted, so overlapping ones are safe.
    - `LeaveModel(uploads: LeavingUploads)` calls `begin` before the server leave and `end` after, whether it worked or failed. The app wires it to the queue, gated on the launch load.
  - **Refused hearts:** a v1 reaction 403 `guest_required` is now fatal for the feed.
    - `FeedModel.Phase.guestRequired` cancels the reaction senders, so nothing is retried.
    - It clears `guestToken` and `participantID` only if the stored participant is this feed's participant (a late answer keeps a newer join). The nickname is kept.
    - The UI shows "You're no longer in this event" and **Join again**, ends the other tabs and hides Share. FR strings were added.
  - `JoinModel.loadEvent` treats `guest_required` on a returning-guest claim as rejected: it clears the identity and asks for a name.
- **Why:** leave means "delete my uploads", and a queued upload must not complete after the server deleted the guest. Before this, a refused heart failed silently on every tap.
- **Review:**
  - Code review: WARN, fixed. The fixes were the cancellation spin, an item left behind on timeout, overlapping leaves, the rejoin after `guest_required`, and test gaps.
  - Security audit: WARN_MONITOR, fixed. The fixes were unloaded records surviving leave, enqueue during leave, and the keychain clear not being bound to the refused participant.
  - **Accepted follow-ups:**
    - Background part tasks and their `.parts` copies are not cancelled on leave. There is no `BackgroundPartUploader.cancel(item:)` yet; the server leave and the orphan sweep clean up R2, and `.parts` is wiped at launch.
    - A guest refused with `guest_required` keeps their queued items. They fail as "join again" and can be retried after rejoining.
    - If the launch load failed, Leave can't remove records (they can't upload without a token).
    - Removing uploads before a leave that then fails is intended; a retry continues.
- **Verified:** `swift test` 457, app `xcodebuild test` 16, device build, `npm run ios:strings:check`.
- **Reference:** branch `feat/ios-leave-cancels-uploads`.

## [2026-11-19] Context Update — Server thumbnails for v1 uploads (slice f1)
- **What changed:**
  - **New route:** `POST /api/v1/events/{slug}/uploads/{id}/thumbnail-url {size}` (needs an owned, open session; rate-limited like part-urls). It presigns a PUT to the session's upload slot `<key>.thumb-upload.jpg`. The URL is signed with `Content-Type: image/jpeg` and `Content-Length: size` (`presignBoundPutUrl`, aws4fetch `allHeaders`), size ≤ 200 KB, TTL 6 h.
  - **Finalize** (`acceptThumbnail`):
    - Reads the slot whole and checks type and size, then that it is a whole JPEG (FF D8 FF … FF D9).
    - Writes the server's own copy to `<key>.thumb.jpg` and stores it as `moments.thumb_key`. Always deletes the slot.
    - A missing, bad or unreadable thumbnail never blocks the moment; storage errors are logged as `thumbnail_check_failed`.
  - **Copy-on-accept:** the served key is never presigned, so a guest can't overwrite an accepted thumbnail with the still-valid URL.
  - **`/media`:** never serves `*.thumb-upload.jpg`. It always sends `nosniff` and `CSP: default-src 'none'; sandbox`, and forces `image/jpeg` on `*.thumb.jpg`.
  - **Cleanup:** both thumbnail keys are deleted on reject, guest cancel and the orphan sweep. `deleteMomentMedia(env, moment)` now deletes `thumb_key`/`display_key`/`poster_key` (admin delete and event purge). Guest leave already did. The event-prefix purge catches everything else.
  - No migration: `thumb_key` already existed (0013), and the feed/media layer already served `thumb_url`.
- **Why:** the plan's thumbnails decision. The app makes a ~400 px JPEG; the feed grid loads it instead of the full photo.
- **Review:**
  - Code review: WARN, fixed (swallowed error now logged, API description for iOS, tests for cancel/409, purge, `/media` headers).
  - Security audit: WARN_MONITOR (post-finalize overwrite TOCTOU, `/media` content-type trust). Fixed with copy-on-accept and the `/media` headers.
- **Pre-launch check for Yassir:** confirm on real R2 that a thumbnail PUT with another Content-Type or a different body size is refused (SignatureDoesNotMatch). If it is not, the only effect is storage abuse at the slot, which is removed at finalize, sweep or purge.
- **Next:** iOS makes the thumbnail and uploads it before complete (f2).
- **Reference:** branch `feat/server-thumbnails`.

## [2026-11-19] Context Update — iOS makes feed thumbnails at import (slice f2a)
- **What changed:**
  - `MediaPipeline.ThumbnailMaker` (internal) writes `thumb.jpg` beside the prepared file:
    - photos come from the prepared upload JPEG (JPEG only, CGImageSource thumbnail at 400 px);
    - videos use their first frame (`AVAssetImageGenerator`, preferred transform, `maximumSize` 400, so a portrait video gives 225×400).
  - Both are redrawn through `PhotoPreparer.normalized` (no metadata or source profile survives), encoded at quality 0.75, then 0.6, 0.45 and 0.3 until the result is ≤ 200 KiB (the server's `MAX_THUMBNAIL_BYTES`), and written atomically.
  - `MediaImporter` returns `PreparedMedia.thumbnail {name, byteCount}`, or nil. A thumbnail never turns a successful import into an error, and only that result says a thumbnail exists (a stale `thumb.jpg` is never trusted).
- **Why:** slice f of the thumbnails decision. Sending the thumbnail is the next slice.
- **Review:**
  - Code review: PASS with minor items. Fixed: `internal(set)`, docs, and tests for quality fallback, retry and portrait video.
  - Privacy audit: WARN_MONITOR, then hardened: the maker is internal and refuses non-JPEG input, and a metadata-absence test covers a tagged source (GPS/EXIF/TIFF) and video.
- **Open:**
  - Until f2b, `thumb.jpg` stays in the item folder until the next-launch sweep. f2b must remove it with the item.
  - `ThumbnailLoaderTests.garbageIsReportedNotCached` flaked once under a full parallel run (counter 1, not 2); it passes alone.
- **Reference:** branch `feat/ios-thumbnails`.

## [2026-11-19] Context Update — iOS sends feed thumbnails with uploads (slice f2b)
- **What changed:**
  - `QueuedUpload.thumbnail: StagedFile?` and `thumbnailSentFor`:
    - Decoding is lenient: older records load, and a non-JPEG thumbnail is dropped rather than failing the record.
    - `nextAction` returns `.sendThumbnail` right after a session opens, before the parts. Sending first matters because the server's finalize sweep can complete a session as soon as its parts exist.
    - `.thumbnailHandled(sessionID:)` marks it done for that session, whether it was sent or failed. A restart (new session) tries again; "Try again" on the same session does not.
  - `UploadQueue.sendThumbnail`:
    - Reads at most size+1 bytes through `StagingArea.open` and requires the exact size.
    - Calls `UploadService.thumbnailURL` (new `MomentsClient` call; https, no userinfo, redacted `ThumbnailURL`), then `ThumbnailSender.send`.
    - Any problem (an unreadable file included) means no thumbnail, counted in `thumbnailFailures`. Only cancellation leaves it for later.
    - The thumbnail file is removed together with the main file.
  - `URLSessionThumbnailSender(hosts:)`: only https to the allowed R2 account host, redirects refused, no cookies or cache. This matches the part uploaders, so a compromised API can't receive guests' pictures. `UploadQueue`'s sender is optional with no default; nil means skip.
  - `UploadModel` queues `PreparedMedia.thumbnail`.
  - Also: `ThumbnailLoader` settles a load's in-flight entry in the waiter. Before, a retry right after a failure could join the failed task until a separate `finish` Task ran. That was the `garbageIsReportedNotCached` flake. The new retry test guards the behaviour but does not reliably reproduce the old race, which depends on scheduling.
- **Review:**
  - Security audit: WARN (thumbnail PUT unpinned and followed redirects; a tampered record could point the thumbnail at the main file). Both fixed.
  - Code review: WARN, fixed (unreadable no longer holds the parts, docs, tests for restart, relaunch and other-session events, a clearer failure test).
- **Reference:** branch `feat/ios-send-thumbnails`.

## [2026-11-19] Context Update — iOS feed grid falls back from a broken thumbnail (slice f3)
- **What changed:**
  - Most of f3 was already in place:
    - the feed and highlights SQL select `thumb_key` (`feed.ts` `MOMENT_COLUMNS`);
    - `media.ts` serves it as `thumb_url`, and `mediaAccess.ts` signs it with `?at=` for private events;
    - the iOS `MomentThumbnail` already tried `thumbURL` first.
  - The missing piece was the fallback. `Media.gridImageURLs` (it replaces `gridImageURL`) lists, smallest first:
    - the thumbnail;
    - then a larger still: a photo's display rendition or original, or a video's poster;
    - never the video file, and no URL twice.
  - `GridImage.load` tries them in order. It moves on only when an image is damaged or gone (`undecodable`, or a 404 as `eventNotFound`). Network, access and server errors stop at once, so an offline guest never starts downloading full photos.
  - The viewer still shows the full file.
- **Why:** finalize only checks that a thumbnail is a whole JPEG (starts with FF D8 FF, ends with FF D9). One that passes but doesn't decode would otherwise show a broken tile for a photo that is fine.
- **Reference:** branch `feat/ios-feed-thumbnails`.

## [2026-11-19] Context Update — web uploads send feed thumbnails (slice f4)
- **What changed:**
  - **Server** (`index.ts`):
    - New legacy route `POST /api/events/:slug/moments/multipart/thumbnail-url {upload_id, key, size}`.
      - Same gates as `part-url`: open upload, `uploadAccess` ownership and join-again, key in the event. App sessions get a 409.
      - It returns a 6 h PUT URL from `presignBoundPutUrl`, bound to `image/jpeg` and the exact size, for the unserved slot `<key>.thumb-upload.jpg`.
    - Web `complete` runs the shared `acceptThumbnail` (whole JPEG, ≤ 200 KiB, copied to `<key>.thumb.jpg`, slot always deleted, never blocks) and stores `moments.thumb_key`.
    - `abort` (for a row that isn't completed) and a failed validation delete both thumbnail keys. The orphan sweep already covered them.
  - **Client** `lib/thumbnail.ts`:
    - `makeThumbnail` draws photos with `createImageBitmap` (EXIF orientation applied) and videos from a `<video>` frame at 0.1 s (5 s timeout).
    - It redraws on a canvas, so no metadata such as GPS survives, and encodes JPEG at 0.75/0.6/0.45/0.3 until it is ≤ 200 KiB.
    - `sendThumbnail` asks for the URL with the guest token, then PUTs with only `Content-Type`, `credentials: "omit"` and `redirect: "error"`. It never throws.
    - `multipartUpload.ts` starts it right after `init`, alongside the parts, and waits for it before `complete` (each request times out after 15 s), for fresh uploads from the page only. A resumed or service-worker upload goes without one.
    - Large photos are decoded at thumbnail width (`createImageBitmap` `resizeWidth`) to avoid a ~190 MB full decode. A video frame is drawn only once `readyState >= 2`.
    - Abort deletes only the never-served slot; a served `.thumb.jpg` may belong to a moment.
    - Checked in Chrome: a 4000×3000 PNG gives a whole 400×300 JPEG, and a WebM gives a 400×225 frame.
- **Review:** security audit PASS (3 LOW items: narrow the abort delete and the request timeout, both fixed; a thumbnail lost if the INSERT fails after acceptance, accepted). Code review WARN, fixed (non-blocking send, memory, readyState, tests for replay, a storage error, cleanup after failed validation).
- **Why:**
  - The web uploads originals uncompressed, so a grid of full files is heavy.
  - The legacy route keeps the deployed client working: old clients never call it, and their moments simply have no thumbnail.
  - R2 CORS (`scripts/r2-cors.json`) already allows `Content-Type` on PUT.
- **Reference:** branch `feat/web-upload-thumbnails`.
