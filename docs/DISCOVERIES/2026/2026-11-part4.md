## [2026-11-19] Context Update — "join again" on a refused guest (slice d2b)
- **What changed:**
  - **Server, one rule:** a presented `X-Guest-Token` the server doesn't know (revoked by a leave, another event's, malformed) gets `403 {code: "guest_required"}`, enforced or not. This covers web upload init (`resolveWebUploader`), every upload follow-up and hearts (`gateReaction`, shared with v1). Only a *missing* token keeps the legacy path until `GUEST_TOKENS_ENFORCED`.
  - `webUploader.ts`: `mayUseUpload`/`mayFinishUpload` (booleans) became `uploadAccess`/`finishAccess` returning `"ok" | "not_found" | "guest_required"`, and `uploadRefusal` maps them to the response. Another guest's valid token on an owned row still reads as 404 "upload not found", so rows don't leak. Enforced plus tokenless on an owned row is now 403 instead of 404.
  - **Client:** `lib/guestRequired.ts`. The upload helpers (`multipartUpload` `jsonReq`, `streamUpload` `jsonRequest`) and `toggleMomentReaction` throw `GuestRequiredError(slug, sentToken)` and dispatch a `moments:guest-required` window event. `EventPage` listens and, **only if the refused token is still the stored one** (`refusalIsCurrent`), runs `forgetGuest(slug)` and shows the gate with `JoinProblem` `"guest_required"` ("join again", EN and FR).
  - Refused uploads are marked `failed`, aren't retried part by part, and aren't handed to Background Sync. The upload worker doesn't reject the sync for them.
- **Review and audit fixes:**
  - Security audit: **PASS**. Code review: WARN, no blockers. Fixes applied:
    - `refusalAction` replaces a plain token compare and returns:
      - `forget` when the refused token is the stored one;
      - `gate` when it was already cleared (left from another tab), so the gate shows without wiping anything;
      - `ignore` when another tab has joined again with a newer token, which is kept, and the refusal counts as an ordinary failure.
    - The upload worker relays refusals to open pages (`postMessage`, validated by `guestRequiredDetail`), because a worker has no `window`.
    - `refused` flag in the multipart worker pool, so a sibling part finishing late can't write a failed row back to uploading or paused.
    - The page's 15 s staged-resume retry skips refusals.
    - During and after a deliberate Leave, refusals are ignored (`isLeavingRef`, set via `LeaveEventButton.onLeavingChange`) until the browser joins again. A dedupe ref guards against several parallel parts reporting at once.
    - v1 reaction 403 description updated, `npm run openapi:update` run (description only).
  - **Accepted:**
    - an enforced tokenless call can tell "owned row exists" (403) from "no row" (404). That needs a 128-bit upload id plus its key, and doesn't reveal the owner.
    - `forgetGuest` drops every saved upload for the slug, as Leave does.
    - The tus create endpoint never checks the token; a dead Stream session there pauses and retries. Pre-existing; follow-up.
    - Stream-path unit tests are still missing: there is no tus harness.
- **Verified:** on local dev, join, then delete the event's `guest_sessions`, then tap a heart. The gate shows "You're no longer joined…", and the event's nickname and token are gone from localStorage.
- **Why:** with enforcement (or after a leave from another tab) a guest's writes would fail with a generic "upload failed" forever. The dead-token "404" is now an explicit 403, so a real 404 keeps meaning "this upload is gone".
- **Impact:** `src/worker/{webUploader,reactions,index}.ts`, `src/client/lib/{guestRequired,api,multipartUpload,streamUpload}.ts`, `uploadServiceWorker.ts`, `EventPage.tsx`, `NicknameGate.tsx`, `i18n.tsx`.
- **Reference:** branch `feat/web-guest-required`.

## [2026-11-19] Context Update — iOS uploads switched on (slice e1)
- **What changed:**
  - **App (`AppEnvironment.startUploads`):**
    - Builds `StagingArea.appDefault()` (Application Support/UploadStaging, completeUntilFirstUserAuthentication re-applied every launch, excluded from backup) and `QueueStore.appDefault()`.
    - One `BackgroundPartUploader` (id `com.moments-hq.moments.uploads`, pinned to R2 account `30062218…`) and the `UploadQueue` with `uploadCredentialsLookup`: no token means "join again", and any keychain read error means "try in 30 s".
    - `live()` is a `static let` (one background session per process). Uploads are skipped under the app-hosted XCTest run.
  - **Launch:** a `.userInitiated` Task runs `UploadLaunch.prepare`, which loads the queue (recovering background tasks), then `StagingArea.sweepItemFolders(keeping: QueueStore.recordIDs(), createdBefore: launch)`. `queue.run()` starts only if the load worked.
  - **Sharing:** `QueueSubmitter(queue:isReady:)` waits for that load, then maps `EnqueueError` to `SubmitResult`: duplicate→duplicate, full→full, file(unreadable)→failed (retry), other file problems→invalid, notLoaded→failed.
  - **Background wake:**
    - `AppDelegate.handleEventsForBackgroundURLSession` hands the system completion to `BackgroundUploadEvents`, which parks it until uploads connect.
    - The connected handler waits for `queue.settle(within: 20)` before releasing it, so finished parts reach "complete" in the wake.
    - `PartTasks` releases a handler that arrives after the session finished its events, and never drops an earlier one.
  - `MediaImporter` item folders get an explicit protection class. The pbxproj links the `UploadEngine` product.
- **Why:** the engine pieces (#36–#48) were built and tested but never connected. This makes "share" work in the app.
- **Review:**
  - Code review: WARN, all fixed. The fixes were a `.notLoaded` window at launch, completion released before the queue acted, `live()` not once-only, and a handler arriving before setup.
  - Security audit: WARN_MONITOR, no exploitable issue. Completion ordering is fixed and protection is re-applied.
  - **Accepted:**
    - the sweep removes folders of quarantined records (they can never upload);
    - the sweep's guard is the folder's creation date (a clock set back mid-run can fail one upload as missing);
    - a permanently failing keychain read keeps its items waiting (bounded by the queue cap, no network calls).
- **Verified:**
  - `swift test` 446, app `xcodebuild test` 16, generic device build, `npm run ios:strings:check`.
  - Simulator launch logs "upload queue loaded: 0 items, 0 deferred, 0 set aside, sweep 0".
  - Not yet: a real-device background upload.
- **Note:** the app's bundle id is still `com.example.moments`. The decided prefix `com.moments-hq` comes with signing and the App Clip phase.
