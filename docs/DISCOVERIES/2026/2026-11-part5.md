## [2026-11-19] Context Update — host sessions (server)
- **What changed:**
  - Migration `0021_host_sessions` and `src/worker/hostSessions.ts`. A token is `hs_` + 32 random bytes; the database stores only its SHA-256, a 30-day expiry, and a `credential_tag`.
  - The tag is an HMAC of the admin credentials under `EVENT_ACCESS_SECRET` (length-prefixed, domain `host-credentials:`). It is checked on every request, so changing `ADMIN_USER`, `ADMIN_PASSWORD` or the secret ends every session.
  - Sign-in compares HMACs with `timingSafeEqual`, so neither the username nor the password length leaks.
  - v1 routes:
    - `POST /admin/session` returns 201 with the token once.
    - `GET /admin/session` returns the subject and expiry.
    - `DELETE /admin/session` deletes the row (204).
  - `hostGate` on `/api/v1/admin/*` requires `Authorization: Bearer`; otherwise it answers 401 `host_auth_required` with `WWW-Authenticate: Bearer`.
  - A `hostSession` http-bearer security scheme is added to the OpenAPI document. The openapi check now requires a `default` response on every operation and a 404 only on `/events/` routes.
- **Why:** Admin sign-in for the app (Yassir, 2026-11-19), with the admin password as the first method. Sign in with Apple and email codes will add rows to the same table.
- **Decisions:**
  - Sign-out deletes the row instead of setting `revoked_at`; the plan's column wasn't needed. Expired rows are deleted on the next sign-in.
  - Without `EVENT_ACCESS_SECRET` sign-in answers 503 instead of failing open.
  - The `ADMIN_AUTH_LIMITER` key is `host-sign-in:<ip>`. **Every** attempt counts, before the password is checked, so a limited client can't tell a right guess from a wrong one.
- **Found:** the web `requireAdmin` (Basic auth) checks the password first and only then counts failures. Once limited, a wrong guess gets 429 but a right one still passes, so the limiter doesn't stop guessing. Its comparison isn't constant-time either. Fix it in its own slice.
- **Audit follow-up:** the limit is per IP only, so many IPs together can still guess. Next comes one global failure counter shared with the web Basic-auth fix. Until then, `ADMIN_PASSWORD` should be long and random. Rotating `EVENT_ACCESS_SECRET` also signs every host out.
- **Next:** the web `requireAdmin` fix plus the global counter, then the iOS admin sign-in (token in the keychain under its own service) and the admin events list.

## [2026-11-19] Context Update — shared admin login lockout
- **What changed:**
  - `src/worker/adminLogin.ts` `attemptAdminLogin` is used by the web `requireAdmin` and by v1 `POST /admin/session`.
  - Steps:
    1. Compare in constant time (SHA-256 of length-prefixed credentials on both sides).
    2. Make **one** D1 batch: a conditional insert (only a wrong password, and only while neither limit is reached, so every locked attempt is read-only), then the counts.
    3. Lock when the failures *before* this attempt are 10 for the client or 100 in all, within 15 minutes.
  - A right password runs the same insert with its condition false and writes nothing. That gives the same work and the same answer (429, `Retry-After: 900`) while locked, and the host's own parallel requests never count.
  - IP hashes are keyed: `EVENT_ACCESS_SECRET`, or `ADMIN_PASSWORD` in local dev.
  - The hourly `pruneAccessFailures` also prunes these rows.
  - The web login shows `adminLoginLocked` (EN/FR) on 429. Migration `0022_admin_login_failures`.
- **Why:**
  - **Security audit HIGH:** the old `requireAdmin` compared first (`===`) and counted only failures, so once limited, a right guess still answered 200.
  - **Review of the first draft:**
    - One client could add rows without end and lock everyone out.
    - Valid parallel requests counted each other's rows written before the check.
    - The DELETE on success was a timing oracle.
- **Decisions:**
  - Web requests without credentials aren't counted.
  - `ADMIN_AUTH_LIMITER` now only guards v1 sign-in (per IP).
  - `verifyHostCredentials` was replaced by `adminCredentialsMatch`.
- **Trade-off and break-glass:**
  - At least 10 addresses guessing together can lock logins for 15 minutes at a time. Existing app sessions are not affected.
  - To unlock: `wrangler d1 execute moments-db --remote --command "DELETE FROM admin_login_failures"` (Yassir only).
- **Lessons:** D1 batches run their statements in one transaction and writes are serialised, so a conditional `INSERT … SELECT … WHERE (SELECT COUNT(*)…) < N` caps rows even under bursts.
